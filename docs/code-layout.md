# Code layout

Back to the [README](../README.md).

Where the code lives, and where a new feature's pieces go. The office used to grow by adding to the middle of a few big files: the server's message switch, the page's key handler, its frame loop and its store. Each of those is a registry now, and a feature is a folder of its own plus one line in each list it joins. If a change has you editing the middle of `main.ts`, `server.ts`, the store or `protocol.ts`, it probably belongs somewhere else.

There are three parts: `src/client` (the page, built by Vite, with three.js), `src/server` (Node) and `src/shared` (types and pure code both use, with no Node imports).

## Client

### `main.ts` and the context

`src/client/main.ts` is the install list: it makes the scene, calls each part's `install…(ctx, …)` in turn, and boots. The order is the order everything registers in (messages, keys, ticks, store topics), and it's kept on purpose, so a new feature's line goes at the end of its group unless it has to come before something.

Every part gets `ctx`: the `Ctx` type in `core/context.ts`, built by `createCtx` in `core/ctx.ts`. It has the scene, the camera, the player, the socket (`net`), sound, settings, what you're holding, the hint bar, `shake`, and the registries. A feature imports `Ctx` as a type and never imports `main.ts` (a test checks). When a part needs another one, it says which: a small `deps` object of callbacks that `main.ts` passes in (`GongDeps` in `features/gong/index.ts`), or a `Pick` of `Parts` (`core/parts.ts`, every part `main.ts` makes, by name). Parts are only read when something happens, never while installing, so a part can reach one installed after it.

### The registries

They're in `core/registry.ts`, and each is a field of `ctx`. Every registration hands back an `Off` that takes it out again.

| Registry | What it's for |
| --- | --- |
| `ctx.messages` | Server messages. `on(type, fn)` runs `fn` once the store has applied the message (`'before'` as a third argument: before it has); `onAny(fn)` runs on every message. |
| `ctx.keys` | Key presses. `add(stage, fn)` for the stages before the office's own keys (`guard`, `activity`, `emote`), and `bind({ code, when, run })` for a key of the office's own. |
| `ctx.ticks` | What runs each frame. `add(phase, fn)`, where the phases run in `TICK_PHASES` order: `pre`, `steer`, `vehicles`, `move`, `moved`, `play`, `me`, `others`, `world`, `env`, `aim`, `hud`, `render`. Within a phase, ticks run in install order. |
| `ctx.activities` | Something you're in the middle of that takes over the controls (the ladder, the golf tee, a car). It gets keys before the office's own, draws the hint bar, and is stopped by `stopAll(why)` when you start something else. Its place among the others is `ACTIVITY_ORDER` in `core/ctx.ts`. |
| `ctx.interactions` | What each kind of thing you can use does: `define(kind, { reach, hint, use })`, once per kind. |
| `ctx.view` | What what you're doing does to your view each frame: something you hold on to, the field of view, covering the screen, or a filter (the drunk vision). |
| `ctx.windowOpened` | What lets go when a window opens (a shot being wound up, the emote wheel). |
| `ctx.usables` | Things to use that aren't part of the building and move about (the pictures, the dog, the ball): what each has to use, and what the aim can land on. |

`tests/client-registry.test.ts` pins how each one orders and dispatches.

### Stylesheets

`style.css` is the 3D office's sheet. It pulls in `styles/base.css` (the colors, the reset, panels, buttons and the window frame, which the 2D view's `lite.css` loads too), `styles/hud.css` and `styles/loading.css`. Every other sheet sits next to its module and comes in with it. A module's sheet loads in no fixed order against `base.css`, so a module rule that overrides a base rule of the same specificity has to be more specific, or live at the end of `base.css` with the others there.

The look is glass, and its tokens are the custom properties at the top of `base.css`: use them rather than a color, a border or a shadow of your own.

- **What floats over the 3D office** (a HUD panel, a menu, a window) is `--glass` (or `--glass-thick` for a window, `--glass-dark` for a hint) with `backdrop-filter: var(--glass-filter)`, a `1px solid var(--glass-border)` edge and one of `--shadow-1` to `--shadow-4`. The `.panel` class is exactly that.
- **What sits inside one** takes `--surface` (a card, a row), `--content` (a page to read: a diff, a doc), `--control` (a button, a text box) or `--wash` (a hover, a sidebar), with a `1px solid var(--hairline)` border. It never gets a blur of its own: a blur inside a blur only sees its parent.
- **A state** has three tokens: the solid (`--good`), the text color (`--good-ink`) and a tint to sit behind that text (`--good-tint`); the same for `--warn`, `--bad`, `--info` and the one `--accent`.
- **Type** is the system font (`--font`) at 400, 500 and 600; corners come from `--r-xs` to `--r-xl` and `--radius`.

The labels that float over people and workers in the 3D office (name tags, bubbles, task cards) are drawn on canvases by `world/toon.ts` in the same glass, with `world/glass.ts`; a sign that's part of the world (`textPlane`) keeps its painted look.

## Server

- **`server.ts`** is the composition root: `startServer` builds the office's context a stage at a time, starts the hook server, opens the floors, and hands the context to the HTTP handler and the WebSocket.
- **`office/`** is that context (`Ctx` in `office/context.ts`: the building-wide services, sending to browsers, the floors, the people in the office, going between floors, and the checks before something happens) and the pieces that make it.
- **`ws/`** takes the sockets. Each domain's messages are handled in `ws/handlers/<domain>.ts`, a map from message type to handler that `satisfies HandlerMap<ItsClientMsg>`, and `ws/handlers/index.ts` puts them all in one `HandlerMap<ClientMsg>`: a message type with no handler, or a handler for a type that doesn't exist, fails the typecheck. The same file lists the features that keep something per person on a floor (`features`: what each lets go of when someone is `leaving` a floor, and once their socket has `closed`) and the pieces of what someone arriving on a floor is sent (`views`, one for each field of `FloorView`, put together by `office/views.ts`).
- **`http/`** answers HTTP from a route table. Each file in `http/routes/` exports its routes, and `http/routes/index.ts` lists them in the order they're tried. Every route says its `auth` (`public`, or `session` for a signed-in browser), and the `Route` type won't let you leave it out.
- **`hooks/`** is the loopback-only hook server the workers call: their agents' hook events (`/hooks/<provider>`), the board agents' queue (`/office/queue`) and `office-workers` (`/office/workers`).
- **`workers/`** is the worker manager (`WorkerManager` in `workers/manager.ts`) and its pieces: worktrees, pull requests, tasks, terminals, ACP workers, and saving to `workers.json`. `src/server/workers.ts` re-exports it for the modules that imported it from there.
- **`providers/`** holds one adapter per agent CLI (see [Adding an agent provider](#adding-an-agent-provider)).
- **`worker-chat/`** is the agent window's server side, behind `http/routes/worker-chat.ts` and `http/routes/shares.ts`: `transcripts.ts` reads a session's messages, `history.ts` keeps the ones sent from the window (a review's with them), `artifacts.ts` is the folder scan and the check every served path passes, `links.ts` the files a worker linked (remembered, and the files beside them), `shares.ts` the folders an admin shares with a floor, `send.ts` sends a message or a review into the worker's session (`sendToWorker`), `review.ts` checks a review and finds its files, and `live.ts` is GPT-Live. A specialist's interface is read from its profile by `roleWorkspace` in `specialists/profiles.ts`.
- **`tunnel/`** is `agent-office tunnel`, the one part that runs on someone's own computer instead of the office's: it asks the office for the workers' web servers (`/api/services`, in `http/routes/services.ts`) and listens on each one's port there. It imports nothing from the office but what the two say to each other (`tunnel/wire.ts`) and the cookie's name.

The rest of `src/server/` is a module per service or per thing a floor keeps (`dog.ts`, `jukebox.ts`, `queue.ts`, `meetings.ts`), made by the office or by each `Floor` (`floor.ts`). `goat.ts` is the building's one goat, Marc: every `Floor` makes its side of him with `goatHome(this, ctx, dataDir)`, and the floors of one office share a herd of one, which decides which floor he is on (the one `goat.json` in the bottom floor's `.agent-office` names, else the first floor). `Goat` is his day (timers, legs sent as `{ t: 'goat' }`, pats, following, riding the elevator, keeping out of the dog's way), and `goat-plan.ts` is the pure half (his grid `goatNav`, `wayTo`, `choose`, `grazeAt`, `nibbleAt`, `buttAt`, `followSpot`, `dogMeets`, `asideFrom`, `homeFloor`), tested in `tests/goat.test.ts`. His messages are in `shared/protocol/goat.ts`, his piece of `FloorView` is `goat` (null on every floor but his), his handler `ws/handlers/goat.ts` and his slice `state/slices/goat.ts`. The hoop's scoreboard is building-wide too, made with the arcade's (`hoopServices` in `hoop.ts`, `ctx.longShots` and `ctx.pig`): `longshots.ts` keeps the table in `hoop.json`, `shot-judge.ts` flies a throw the office's way and checks it left the thrower's hands where they stood, and `pig.ts` runs a game of PIG on each floor that has one (the rules are pure in `shared/pig.ts`, the table's in `shared/longshots.ts`); its messages are in `shared/protocol/hoop.ts`, its handler `ws/handlers/hoop.ts` (which the ball's handler asks before and after a throw), its piece of `FloorView` is `hoop` and its slice `state/slices/hoop.ts`. `watch.ts` is a building-wide service like `feeds.ts` (made in `office/services.ts`, `ctx.watch`): it resolves pasted YouTube links to channel ids and reads each channel's feed. Its piece of `FloorView` is `watch`, its message `{ t: 'watch' }` (`shared/protocol/watch.ts`) and its slice `state/slices/watch.ts`.

## Shared

- **`protocol.ts`** is the wire protocol. It puts the domain files in `protocol/<domain>.ts` back together (`export *`) and makes the `ClientMsg` and `ServerMsg` unions every frame is one of. Keep `import type` between domain files: some name each other's types (`floors.ts` and `presence.ts` do), which only type imports can do without a cycle at run time.
- **`providers.ts`** is the provider table: every agent a worker can run, and what the office knows about each.

The rest is data and pure code both sides use: the floor's layout, the office's plan (`shared/maps/`: `OFFICE_PLAN`, a `MapPlan`, where every seat and board is by id, which the client reads through `ctx.plan()` and `store.plan()`), the sun, the garage and so on. `shared/youtube.ts` reads YouTube links (`youtubeId`, `channelLink`) for both sides; a screen that follows the floor's channels has `media: '@watch'` (`WATCH_MEDIA` in `shared/furniture.ts`).

`shared/clerestory.ts` is the twelve upper windows (`CLERESTORY`, spread into `WINDOWS` in `shared/layout.ts`) and `columnsOf(holes)`, which puts the windows on a wall that share a span into a column, from the bottom up: the office's walls and the tower's planes are painted round columns, so one window can stand over another.

What's built into the office floor depends on the floor's room options (`RoomOptions` in `shared/floorplan.ts`: tees, `mezzanine` 'none' | 'corner' | 'big', `boss`, `kitchen`, `panels`, `wood`, `meeting` 'room' | 'forum' | 'desk', `steps`, `ceiling` 'tiles' | 'beams' | 'banners' | 'grid', `flights` 1 | 2; `roomOf(plan)` works them out in full as a `FloorRoom`, and `cleanRoom` keeps only what isn't the default). `shared/mezzanine.ts` is the upstairs as data: `mezzanineOf`, `hasBoss`, `hasKitchen`, `structureKey(room)` (two rooms with the same key are the same floor to get round: it goes by the upstairs and its flights, the boss's office, the kitchen, the meeting place and the Steps, and not by the ceiling, which nothing walks round), `deckOf(room)` (the slab, the floor to furnish, each flight of stairs, the posts), `flightsOf(room)` and `bigFlights(room)` (which of `BIG_FLIGHTS` a floor has: the second, at the west end, only when it asks for two) and `deckSolids(room)` (the big mezzanine's colliders with those flights, shared by the 3D office and the tests). `fixedIn(room)`, `keepClearIn(room)` and `keepClearUp(room)` in `shared/office-fixed.ts` go by it. `validateLayout`, `layoutProblems`, `problemAt` and `structureProblem` (`shared/office-builder.ts`), `officeNav` (`shared/nav.ts`) and `floorSeat` (`shared/furniture.ts`) all take the room, and a caller that passes none gets the office as it comes. The server passes each floor's own; a browser, which shows one floor, sets it with `setOfficeRoom` where the layout is applied (`features/office-builder/sync.ts`, which sets the 3D office's room first, `office.room.set(roomOf(a))`, and then stands the furniture).

`shared/meeting-place.ts` is where a floor's workers meet: three presets (`'room'`, the glass room the office comes with; `'forum'`, a panel table on a stage in front of the TV; `'desk'`, an anchor desk with a prompter). `meetingOf(room)` says which, `meetingPlace(room)` is the whole place (its table, the five seat poses, the output board, the sign, where each is used from, what is in the way and what is kept clear, and what it's called), and `meetingSeats(room)` hands back the five seats at that place as fresh copies under the same ids, `meeting-1` to `meeting-5`, so `server/meetings.ts` never has to know. `MEETING_ROOM`, `MEETING_TABLE`, `MEETING_SEATS` and `MEETING_BOARD` in `layout.ts` are the glass room's numbers. The server keeps several floors at once and asks `meetingSeats(room)`; a browser shows one, and stands the shared `MEETING_SEATS` at the floor's own place (`features/office-builder/sync.ts`, and `world/office/meeting-place.ts` with what you see of them). A floor's meeting place only moves while none of its five seats is taken (`server/floorplan.ts`). `ui/whereabouts.ts` says who's there by the place's own `area` and `where`.

`shared/steps.ts` is the Steps, a six-tier amphitheatre across the lounge for a floor with `steps: true`: `STEPS` (its numbers), `STEPS_RECT` (the floor it takes, which `fixedIn` blocks for whoever walks by the grid), `onSteps(x, z)`, `stepsSolids()` (what you bump into, shared by the 3D office and `tests/steps.test.ts`) and `stepsSeats()` (a bench per tier, `steps-1` to `steps-6`, which `floorSeat` finds on a floor that has them, and which a browser stands in `SEATING` with the furniture's seats only on such a floor).

A piece with `level: 1` stands upstairs (`pieceY`, `canGoUp`, `pieceTop` in `shared/furniture.ts`): it is checked against the deck's floor and only gets in the way of other upstairs pieces, and the way round the floor ignores it. A `painting` is a piece that hangs (`KindDef.hangs`): its size is `hangSize` (`shared/hangings.ts`), and it must be on a face from `wallFaces(furniture, level, room)` (`shared/wall-faces.ts`: the outside walls and both sides of every wall piece), which the builder snaps to with `snapToFace`. `shared/mezzanine-rooms.ts` has `starterRooms()`, the 26 pieces the builder drops on an empty big mezzanine. `shared/panels.ts` has `panelRegions(side, plugged)`, the rectangles of an outside wall its wood covers (the wall less its openings). A `ceiling-panel` is a piece that hangs from the office's own ceiling (`KindDef.overhead`, 2.4 m square): nothing bumps into it, and it can't go upstairs, under the big mezzanine or the corner loft, over a flight of stairs or through the elevator's shaft (`hungThrough` in `shared/office-builder.ts`). Where the pictures people hang with F may go follows the room too (`zonesFor(room)` in `shared/decor.ts`). `FLOOR_PALETTES` (`shared/floors.ts`) has more paints than a new floor is ever handed: only the first `STOCK_PALETTES` are given out, and the rest are for the builder to pick. The balcony's tee bays are in `shared/tees.ts`.

A new option for the room is a field of `RoomOptions` and `FloorRoom` (with its default in `ROOM_DEFAULTS` and its line in `cleanRoom` and `roomOf`), a fixture that follows it, and its choice in `features/office-builder/room-ui.ts`. If it changes what's built in or where there is to walk, it also goes in `structureKey`, `fixedIn` and `keepClearIn`, and `structureProblem` (`shared/office-builder.ts`) names what a refused change is for: *Clear upstairs first*, *Clear the floor for the kitchen first*, *for the meeting place first*, *for the Steps first*, else *for the mezzanine first*. The builder's draft and the office's save both ask it, so they refuse in the same words. If it brings somewhere to sit, its seats go in `floorSeat` and in what `sync.ts` hands `setFloorSeats`; if it can come or go under someone, `sync.ts`'s `settle` puts them down or steps them out.

## Adding a feature

A new feature adds files of its own and one line in each list it joins. For something on the floor that everyone there sees and uses, that's:

1. **Its messages** in a protocol domain file (`src/shared/protocol/toys.ts`, say). A new domain file also goes in `protocol.ts`: its `import type`, its `export *` and its members of the unions.
2. **A server handler file**, `src/server/ws/handlers/<name>.ts`, and its line in `handlers` in `ws/handlers/index.ts`. If it keeps something per person, its `FeatureHooks` go in `features` there; if people arriving on a floor need its state, that's a field of `FloorView` (`protocol/floors.ts`) and its piece in `views`. What a floor keeps is a module of its own in `src/server/`, which `Floor` makes.
3. **A state slice**, `src/client/state/slices/<name>.ts`, and its line at the end of `SLICES` in `state/slices/index.ts`.
4. **`src/client/features/<name>/`** with its `install<Name>(ctx, deps)`, and its line in `main.ts`. If another part needs what it returns, a line in `Parts` (`core/parts.ts`) too.
5. **What you can use.** The file that calls `ctx.interactions.define('<kind>', …)` also adds the kind, by augmenting `InteractKinds` in `world/types.ts` (`declare module '../../world/types'`); `tests/client-registry.test.ts` checks every kind is defined once, in the file that adds it. Something that stands in the office is a fixture: `export const <name>: Fixture<'<field>'>` in its `world.ts`, which adds the field it gives `Office` to `OfficeHandles` the same way, and a line in `floorPlan()` in `world/office/build.ts` (which won't typecheck while a field in `OfficeHandles` has no fixture giving it). `features/gong/` does both.
6. **A help row** in `HELP_ROWS` in `src/client/ui/help.ts`.
7. **A sound recipe** in its `sound.ts` (a function or class that takes the `AudioCore`), and the method on `OfficeSound` that plays it.
8. **Its CSS** next to its ui module, imported from there.

Its HTTP routes, if it has any, go in `http/routes/`, and its tests in `tests/`.

## Adding an agent provider

One adapter file in `src/server/providers/`, one entry in `PROVIDERS` in `src/server/providers/index.ts`, and one row in `src/shared/providers.ts` (its id in `AGENT_PROVIDERS`, its entry in `PROVIDER_META`). The typecheck fails until all three are there. Its row says which models and efforts it takes and how the hire dialog asks for them; one whose CLI lists its models gets a lister in `src/server/models.ts` too. What reads them, and the one place that still names providers one by one, are in [Provider seams](dsh-acp-integration.md#provider-seams). A new provider wears the plain emblem on its antenna until it has a row in `TOPPERS` (`src/client/world/toppers.ts`); that row is optional, and nothing fails without it.

## The size guard

`tests/size.test.ts` holds every `.ts` and `.css` file under `src/` to 600 lines. It asks `git ls-files` for them (tracked, and new ones that aren't ignored) rather than walking the folder, so a worktree checked out inside the repo can't trip it. The files that were longer when it came in are listed in `CEILINGS`, each with the length it had then: they may shrink, but never grow past it. Once one is down to 600 lines or fewer, or gone, the test fails until you take it off the list, so the list only gets shorter.

When it fails, split the file along the registries: a feature's code goes in its folder, a message handler in its domain's file, a tick or a key in the feature it's for, and what the page keeps of it in its own slice. Raising a ceiling, or adding a file to the list, only hands the problem to the next person, so the honest way to make room is to split the file. When you shrink a listed file, lower its ceiling to its new length in the same change, so it can't grow back.
