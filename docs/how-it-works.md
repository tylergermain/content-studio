# How it works

Back to the [README](../README.md). [Code layout](code-layout.md) says where the code lives, and how a feature plugs in.

```
browser ──HTTPS/WSS──▶ agent-office (Node)
                         ├─ node-pty ─▶ claude / opencode (one PTY per worker, cwd = project dir)
                         │    └─ headless xterm mirror ─▶ laptop screen frames + late-join snapshots
                         ├─ loopback-only hook server ◀── curl from Claude Code hooks (per-worker token)
                         ├─ gh issue/pr list (cached, refreshed every 90s)
                         ├─ port scan every 4s ─▶ 🌐 Services board; relay for service tunnels
                         │    └─ /api/services ◀── agent-office tunnel on your computer: localhost:<port> for each
                         ├─ /api/image ─▶ fetches pictures for the walls (cached)
                         └─ WebRTC signaling relay (voice, screen share and webcams are peer-to-peer)
```

- **Status.** Claude workers start with `--settings .agent-office/claude-hooks.json`. That file adds hooks (`UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PermissionRequest`, `Notification`, `Stop`, `SessionStart`) which `curl` a server bound to `127.0.0.1`. The hooks merge with your own Claude settings; they don't replace them. OSC 9;4 progress sequences in Claude terminals also count, which catches an Esc-cancel. OpenCode workers use a generated plugin to forward session, permission and question events to the same loopback server, with a separate endpoint. Codex uses a generated command helper and its own authenticated endpoint. The server reads only token records from the explicitly linked root rollout; approval settings are preserved. DeepSeek Harness workers report through the ACP session itself: `session/prompt` in flight is *working*, an outstanding `session/request_permission` is *needs input*, and a settled turn is *done*, with no hooks and no polling.
- **Shared shells.** Press **B** at an empty desk to open a plain login shell for dev servers, git or tests. It's shared the same way as a Claude terminal.
- **Isolated branches.** When you hire with a task, you can tick *own git worktree*. The worker then gets its own `office/<name>` branch under `.agent-office/worktrees/`, so parallel workers never share a checkout. The branch starts from what the office's branch is on GitHub: just before cutting it (a hire, a queue task, a meeting), the office runs `git fetch origin <branch>` (`src/server/worktrees.ts`; a burst of hires shares one fetch) and branches from `origin/<branch>`, so pull requests merged since anyone pulled are in it. It branches from the local `HEAD` instead when that already has all of it (it's ahead with commits not pushed yet), or when there's no origin or the fetch fails. When both have moved on, it starts from origin's and a toast says how many local commits it left out. The project's own checkout is never moved, and the Changes window diffs against whichever of the two is newer. When you send that worker home you choose whether to keep the worktree and branch, delete the worktree, or delete both, and the office warns you first about uncommitted changes or commits no remote has. `agent-office prune` clears out whatever was kept, once it is safe. A worker whose folder (its worktree, or its workspace) is gone is never started there: `checkLost` in `src/server/workers/worktree.ts` looks before every start and every 10 seconds, and sets `WorkerInfo.lost` with where its branch still is (`here`, only on `origin`, or `gone`), with no toast. `worker.rebuild` (`all` for every lost worker on the floor) runs `git worktree prune` and `git worktree add` at the same path, on the branch, else `-b <branch>` from `origin/<branch>`, else from its base commit (`Worktrees.restore`), rewrites a workspace's brief, and restarts everyone who worked in that folder (a meeting's table too) with `--resume`; one whose process was still running in the deleted folder is stopped and resumed there. A folder put back by hand clears the mark by itself. With *Workers whose pull request merged* set to go home by themselves (`src/server/leave-on-merge.ts`, saved in `.agent-office/leave-on-merge.json`), each floor looks again whenever the PR list comes back, a queue task's PR is linked or a worker changes, and uses the same call as the purple bubble (`workerPr` in `src/shared/status.ts`). A worker goes with the office's usual check for work its worktree would lose, except that commits up to the merged PR's head count as delivered, even once GitHub has deleted the branch.
- **Pull requests.** **O** at a worktree worker's desk runs `git push -u origin office/<name>` in its worktree, then `gh pr create` with the task as the body and the commits listed. The base is the branch the office was on when the worktree was cut, if that branch is on the remote. The PR number is saved with the worker, so the board can point back at the desk.
- **Across repositories.** A worker hired with other floors' projects (`WorkerInfo.repos`, `makeWorkspace` in `src/server/workers/worktree.ts`) gets a workspace folder, `.agent-office/worktrees/<name>/` on its own floor, with `git worktree add -b office/<name>` of its own project and of each other one in it, named after their checkouts. Each is cut from that checkout's HEAD, and its `from` branch is what the project's PR targets. The workspace isn't a repository; the agent starts there with `GIT_CEILING_DIRECTORIES` set to its parent, so git run in it finds nothing instead of the floor's own checkout, and the `worker.repos` prompt is written there as `CLAUDE.md` and `AGENTS.md`. If one project can't have its worktree, the ones already made are removed again. **O** pushes and runs `gh pr create` in each worktree that has commits and no PR yet (the issue's `Closes #n` only in the home project's; the others say `Part of owner/repo#n`), then puts a list of all of them between `<!-- agent-office:related -->` markers in each one's description with `gh pr edit`, replacing the list on later presses. A worker across repositories goes home by itself once no PR of its is open on any floor's board, one has merged, and none of its worktrees holds work those merges didn't deliver. `agent-office prune` leaves a workspace alone while worktrees are in it, and in the other projects lists the worker's branch as checked out elsewhere (and prunes it once that office no longer lists the worker).
- **Changes.** While someone has a desk's Changes window open, the office runs `git status` and `git diff` in that worker's checkout every two seconds and pushes the file list when it differs. The diff is against the merge base with the branch the office was opened on, so it covers the worker's commits and its uncommitted edits. Commit is `git add -A && git commit`, discard is `git restore` / `git clean` (or `reset --hard` for everything), and Open PR pushes the branch and runs `gh pr create`.
- **Shared terminals.** Each worker's PTY lives in `agent-office-ptys` (`src/server/ptyhost.ts`), a detached process the server starts for each floor and talks to over a Unix socket in that project's `.agent-office/`. On SIGTERM the server leaves the PTYs running there, and the next server takes them back with a snapshot of each screen. Hooks that fire in between retry until it's up. If no server comes back within 30 minutes, the PTYs are ended. The server mirrors each PTY in a headless xterm. People who open the terminal get a serialized snapshot, then the live stream. Laptops get compact per-row diffs a few times a second. The PTY takes the size of whoever is typing.
- **Scrollback and search.** Every 15 seconds, for each worker that printed something new, and again as the office shuts down, its last 3,000 lines are serialized, colors included, to `.agent-office/scrollback/<worker>.ansi`. A worker that starts again (after a restart, or when you resume it) gets its old lines replayed into its terminal first, then a dim *office restarted* line. The chat is appended to `.agent-office/chat.jsonl` and trimmed to the last 1,000 messages. `GET /api/search?q=` matches case-insensitively, treating runs of whitespace as one space, over the chat and each worker's terminal buffer. It returns the newest lines first, each distinct line once. The browser finds the hit again in its own copy of the terminal and scrolls to it.
- **Cost.** Hooks carry no usage, but each one names the session's transcript (`~/.claude/projects/<dir>/<session>.jsonl`). The office reads what gets appended to it, and to the subagent transcripts next to it: every assistant message records the API's token usage and the model, which the office prices from its own table (cache writes and reads included). The model of the session's own latest message (not a subagent's) is also what the worker's card says it runs on. When a session ends, Claude Code appends its own tally (`cost-state`), and the worker's numbers snap to that, which also covers calls that never reach the transcript. Per-worker totals are saved with the worker, and `.agent-office/usage.json` keeps the office's all-time and per-day spend, so nothing is lost on a restart or when a worker is sent home. On an office deployed with `deploy/aws.sh`, put `AGENT_OFFICE_BUDGET=20` (and `AGENT_OFFICE_BUDGET_PAUSE=1`) in `/etc/agent-office/env` and restart the service.
- **The holiday theme.** The server keeps the building's pick (`src/server/theme.ts`, saved in `.agent-office/theme.json`) and, for *By the calendar*, works out the holiday from the office's clock, checking again every ten minutes. Each browser then dresses its own scene: the costumes are in `src/client/world/costumes.ts`, the decorations in `src/client/world/holiday.ts`, and Christmas's snow in `src/client/world/sky.ts`.
- **Sky.** The server decides the weather and tells everyone (`src/server/sky.ts`), and each browser works out where the sun is from that and the office's clock, sped up so a whole day and night go by every hour (`skyTime` in `src/shared/sun.ts`: midnight on the hour, noon at half past, on today's date so the days are as long as the season's). Without `--city`, the office sits in the middle of the host's time zone at 40° north (34° south if its clocks go forward in January), and the weather changes every 20 to 50 minutes, with the season's odds. With `--city` (a name, or `lat,lon`), it asks open-meteo.com for the place once and for its current weather every 15 minutes; no key is needed, and nothing but the city's name and coordinates is sent. The office has no roof, so the sun and the sky light the rooms too. At night a few lines added to every lit material put lamplight back in the office and the garage, and pools of light around the lamps outside (`src/client/world/sky.ts`). A server on AWS keeps UTC, so on an office deployed with `deploy/aws.sh`, put `AGENT_OFFICE_CITY="Portland, Oregon"` in `/etc/agent-office/env` and restart the service for your own weather and calendar.
- **Services.** Every 4 seconds the office lists the TCP ports its user's processes listen on (`ss`, or `lsof` on macOS). It credits each port to the worker whose terminal started it. It goes by the process tree first. For a server that detached from it, it uses the `AGENT_OFFICE_WORKER_ID` the process inherited (Linux), then whether it runs inside that worker's worktree. Ports that answer HTTP are shown. A request for `localhost:<port>` that reaches the office's own port (that's what a service tunnel does) is relayed to that server, WebSockets included, so hot reload works. On a Tailscale office (`AGENT_OFFICE_TAILSCALE_HOST`, set by `deploy/provision.sh --tailscale`), a request for `<office>.ts.net:<port>` is relayed the same way, with `localhost:<port>` as its Host so dev servers that check it let it in. Whenever the list changes, the office has Tailscale Serve point exactly those ports at itself, through the `agent-office-serve` helper (`src/server/tailnet.ts`). `agent-office tunnel` ([Workers' servers on your own computer](tunnel.md), `src/server/tunnel/`) runs on someone's own computer: it asks the office for the list every 2 seconds (`/api/services`), listens on each port there, and sends what arrives to the office with its own session and an `x-agent-office-service: <port>` header, which the office relays like a request for `localhost:<port>`. That header is how it works whatever address the office has. In a container (Railway, Fly.io, Dokploy) the image brings `ss` along, which the scan needs.
- **Pictures.** WebGL can only draw an image from another site if that site sends CORS headers, and most don't. So the office fetches each picture itself (`/api/image`, images up to 15 MB) and serves it from its own origin. Any image link works, and a picture on a worker's dev server does too. Browsers shrink each one to 1024 px before it goes on the wall.
- **Webcam faces.** Your webcam goes browser to browser like voice, on the same `RTCPeerConnection` to each person on your floor, or, where the office has a TURN server (`--turn`) and the two browsers can't reach each other directly, through that relay, still encrypted end to end (DTLS-SRTP), so the relay can't see it either. The office never decodes or records the picture: all it keeps is a flag on your `PeerInfo` (`webcam`, set by `{ t: 'webcam' }`, `src/server/ws/handlers/webcam.ts`) so everyone knows to look for it, and it relays the connection's signals as it does for voice. Nothing of it is recorded or stored, on the office's machine or anywhere else. The browser asks the camera for a 240×240 square at 15 frames a second (`features/webcam/logic.ts`), and it goes out capped at about 150 kbit/s (`CAM_ENCODING` in `src/client/voice-camera.ts`). It's a video line of its own, apart from the screen share's, so both can be on at once: made by whichever side turns its webcam on first (a new connection is given 1.5 s first, for whatever the other side opens it with, and the polite side waits a second more, so two people turning theirs on at once share one line instead of offering two across each other), and answered open both ways, so the other side's webcam goes on the same line. After that a webcam goes on and comes off with `replaceTrack`, which isn't negotiated. Every signal names the line the sender's webcam goes on by its mid (`cam`), so the other side knows what arrives on it for a webcam, not a share, before it arrives, and a share that lands on that line the other way round (two offers crossing can do that) is still a share. A share never goes on a webcam's line, ours or theirs (`isCamLine`): while one is a line `addTrack` would take (nothing of ours on it, never agreed to send on, as theirs is while their offer of it is being answered), `Voice.carry` makes the share's line with `addTransceiver`, which never takes a line that's there. Any other time a share, and a mic always, goes on with `addTrack`, so a line of its kind that the other side's offer brings at that moment takes it, rather than a second line being made beside theirs that they'd answer open and send nothing on, and that you'd then hear (or see) instead of theirs (tested in `tests/voice-glare.test.ts`, and with two real browsers in `tests/support/rtc-glare-browser.mjs`). A browser that won't take the cap on a line it didn't make (`setParameters`) is asked three times on that connection and then left alone. Who it goes to is looked at five times a second, on a timer rather than the frame, so it still is (about once a second) while your tab is in the background and draws nothing: only the 8 nearest people on your floor within about 26 m (it stops past 28 m), and each face that shows one plays it within 25 m, only for the 8 nearest faces that have one, and is paused on its last frame past 27 m, so someone across a big floor is never decoded at all and a crowd costs no more than a few people near you (`MOST` and `Nearest` in `features/webcam/logic.ts`). A face shows the middle three quarters of the picture's middle square (`FACE_ZOOM`), so up close it reads as a face rather than a head seen through a porthole. While your webcam is on, your picture in the corner and **📷 On camera** stay on screen even where the rest of the HUD is hidden: looking through the telescope, and in the office builder. Nobody needs to have joined voice for it: the connections are there between everyone on a floor either way, voice only adds the mic to them.
- **Whiteboard.** It syncs the way Excalidraw's own live collaboration does. Every change bumps an element's version, each browser sends the elements it changed over the office's socket, and everyone merges what arrives with Excalidraw's `reconcileElements`, keeping the newer copy of each element (equal versions go to the lower random nonce, so every copy agrees). The office applies the same rule to its own copy and saves it in the floor's `.agent-office/whiteboard/elements.json`. Deleted elements are kept for a week so a deletion reaches everyone. Pictures go up once over HTTP (`/api/whiteboard/file`, up to 6 MB each) and are fetched by id, a hash of the picture. Excalidraw, a few MB of JavaScript, only loads when someone opens the whiteboard or a floor has a drawing to show on the board, and its fonts are served by the office rather than a CDN.
- **Voice and screen sharing.** Browser to browser, one `RTCPeerConnection` for each pair of people on a floor (`src/client/voice.ts`); the office only relays their signals (`{ t: 'rtc' }`). A connection keeps one line for audio and one for video, each made the first time either side sends that kind and answered open both ways, and a mic or a share goes on its line and comes off it with `replaceTrack`, which the two sides don't have to negotiate. So two people changing the same connection in the same moment (someone sits down across the boss's desk and is put on the call just as the boss's game starts going out to them) mostly have nothing to collide over. What is negotiated, a line that isn't there yet, follows WebRTC's "perfect negotiation": when both make an offer at once, the one whose id sorts first (the polite side) gives way, and each side applies the other's signals one at a time, in order. It never gives way by rolling its offer back, because Chrome (154) loses tracks there: after a rollback on a connection that had agreed on nothing it refuses every later offer from that side (`A BUNDLE group contains a codec collision for header extension`), and on one that had, what that side was sending stops. With nothing agreed on yet, the polite side takes a new `RTCPeerConnection` and answers on that; otherwise the connection is started over on both sides, which is also what happens when an offer or an answer won't apply at all (up to three times in a row). Every signal carries how many times its connection has been started over, so one for a connection that's gone is dropped, and a higher count than your own is what tells you to start yours over. `tests/voice-glare.test.ts` runs all of that against a stand-in browser (`tests/support/rtc-fake.ts`), and `node tests/support/rtc-glare-browser.mjs` runs it in two real headless Chromes, a share and a mic in the same moment, twenty times with each side polite.
- **Board agents.** Each kiosk is a seat of its own (`station-issues`, `station-pulls`, `station-queue`) that the desks, the bean bags and the queue never use, and its agent doesn't count against the queue's *workers at once*. Its first prompt starts with a brief (`src/server/stations.ts`) saying what it's for. The agents reach the queue with `office-queue` (`bin/office-queue.js`, plain Node), which the office writes into the floor's `.agent-office/bin/` and puts first on their `PATH` whichever agent runs them: `office-queue list` shows each task's id, status, title, worker and PR, `office-queue add --title "…" [--issue 12]` queues a task with its prompt on stdin (or `--prompt`) and prints its id, and `office-queue remove <id>` takes a waiting one off. Under the hood that's `GET`, `POST` (`{title, prompt, issue?}`) or `DELETE ?task=` on `$AGENT_OFFICE_HOOK_URL/office/queue?worker=$AGENT_OFFICE_WORKER_ID` with `Authorization: Bearer $AGENT_OFFICE_HOOK_TOKEN`, all three set in their environment, over the office's loopback hook port. Only a board agent's own token is accepted; anyone else gets a 401 or 403, which the command prints. The queue agent is told to only ever add tasks, and with Claude Code it's also launched (and resumed) with `--disallowedTools Edit Write NotebookEdit`, so it can't edit the checkout's files.
- **Workers managing workers.** `/office/workers` on the same loopback hook port (`src/server/office-workers.ts`, the handler beside `/office/queue` in `src/server/hooks/`) lets any running worker, not only a board agent, act on its own floor with its own `?worker=` and bearer token. `GET` lists every worker as a row: desk, status, task, worktree branch, its PR (`workerPr`), `merged` (a PR of its merged and none is open, `landedWork` in `src/server/leave-on-merge.ts`) and `staying` (why *go home once merged* wouldn't take it yet, `notLeaving`). `POST` hires one at the next free seat, running as whoever the asking worker runs as, in a worktree cut after a fresh fetch. `POST /home` takes `{workers: [names or ids]}` or `{merged: true}` (the leave-on-merge rule, with anyone skipped listed and why) and `cleanup` (`auto`, `keep`, `worktree`, `all`). It sends them home one at a time through `Floor.sendHome`, which passes the merged PRs' heads to `kill` so a squash-merged branch whose remote was deleted still counts as delivered. `POST /tell` types a prompt, or wakes a stopped worker with it. A worker can't send itself home or tell itself. `POST /pr` takes `{pr, worker?}` (a number or a URL; the asking worker when it names none) or `{unlink: true, worker?}` and sets that worker's `pr`, the same field **O** at its desk sets. The pull request has to be open, or merged and still on the floor's list (the last 30 merged), in the floor's own repository. That's for the pull requests the office can't place by itself: `workerPr` goes by `pr`, the worker's queue task, or its worktree branch, and a worker in the main checkout has no branch the office knows. A Claude Code worker's `pr` is also set from its hooks: a `PostToolUse` (or `PostToolUseFailure`) for a shell command that runs `gh pr create` and prints a pull request URL in the floor's repository (`ownPr` and `WorkerPrs.noteOwn` in `src/server/workers/pr.ts`). When it opens another, the earlier ones stay its own (`pastPrs`), so one still open keeps it from counting as landed. The other agents' hooks name the tool but not what it ran, so theirs need `POST /pr`. `bin/office-workers.js` (plain Node) is both the `office-workers` command, written into `.agent-office/bin/` and put first on every worker's `PATH` (board agents get `office-queue` from there too), and, as `office-workers mcp`, a stdio MCP server named `agent-office`. Claude Code gets it with `--mcp-config .agent-office/agent-office-mcp.json` (placed before `--settings`, which ends that flag's list), and the hook settings allow `mcp__agent-office__list_workers` without asking. Codex gets it with `-c mcp_servers.agent-office.*`, plus `env_vars` so it hands the server the `AGENT_OFFICE_*` variables, which it otherwise wouldn't. OpenCode gets it in `OPENCODE_CONFIG_CONTENT`'s `mcp`. Grok, Muse and DeepSeek Harness workers have the command only.
- **Meetings.** A meeting (`src/server/meetings.ts`, patterns in `src/shared/meetings.ts`) seats its workers at the meeting table's chairs (`meeting-1` to `meeting-5`), which only a meeting uses, in one git worktree of its own on an `office/meeting-…` branch that everyone at the table shares. Each round is one or two steps; in each step, every worker with a part gets it as a prompt (the first one comes with a brief: the pattern, the roles, the question, the bounds), and the step is over when each of them has ended its turn (the same `Stop` hook and idle events as the status) with the file its part names written since it was handed over. Notes go in a `.meeting/` folder at the top of the worktree, where the others read them (not under `.agent-office/`, where Claude Code asks before writing in a worktree nested in the project), and are copied into the floor's own `.agent-office/meetings/<id>/` when the meeting ends. A worker that ends its turn without writing its file is reminded once; the second time, the meeting stops. Nothing stops a meeting for what it uses: the tokens and cost on the door's sign and in the meeting window are the workers' own figures added up (everything their sessions report, cache reads included, so they climb by a session's whole context with every call). When the output file is written, the office runs `git add -A` (all but `.meeting/`) and `git commit` in the worktree, or for a review panel posts the file as a review with `gh api …/pulls/<n>/reviews` (`event=COMMENT`). Workers waiting on the meeting don't jump or ding when they finish a part, and they don't count against the queue's *workers at once*. `meetings.json` keeps the meeting and the ones before it, so a meeting carries on through a restart of the office, like its workers do. Clearing the room sends the workers home and removes the worktree, keeping the branch when it has the committed output, and everything when something is left uncommitted.
- **Task queue.** `queue.json` holds the tasks and their providers in order. A task is seated when a desk is free and fewer than the limit are busy (a worker that is starting, ready, working or waiting for input). It finishes when its worker ends its turn (Claude/Codex `Stop` hooks, OpenCode's idle event, or DeepSeek Harness's settled `session/prompt`), stops, or is sent home. The PR is matched by GitHub's closing-issue references (`closes #12`) or by the worker's branch.
- **Bookshelf.** `src/server/docs.ts` lists a floor's Markdown (`.md` and `.markdown`) with `git ls-files --cached --others --exclude-standard`. That covers what's committed plus new files that aren't ignored, so `node_modules`, build output and `.agent-office/` stay off the shelf. A folder that isn't a git checkout is walked instead, skipping hidden, dependency and build folders. Each doc's title is its front matter `title:` or its first heading, read from its first 4 KB, and the list is cached for a few seconds (`/api/docs`). Only Markdown can be read (`/api/docs/file`, up to 2 MB), and only pictures can be fetched for a doc (`/api/docs/picture`), both inside the checkout after following links. The browser renders the doc with the same sanitizer as issue and PR text. The book in your hands is the `reading` flag the office keeps on you while the window is open.
- **The dog.** Each floor's dog lives in the office, which decides what it does next: a worker waiting on an answer first, then napping by a busy worker, following someone, sniffing about or lounging. It walks around the furniture along a route found on a half-meter grid of the floor (A*, then pulled tight), and the office sends one message per leg of its day: the route, its speed and what it does at the end. Every browser works out from that where the dog is at any moment, so everyone on the floor sees it in the same spot without a stream of moves. The barks are timed in the browser, from when it arrived at the desk. A worker sent home finds its way to the exit door (or, on the floors above the bottom one, the balcony doors) on the same grid, worked out in each browser when the office says the worker is gone.
- **The goat.** The building has one goat, Marc, where every floor has a dog. Each floor makes its side of him, and the floors share a herd of one that says which floor he is on: the one `goat.json` in the bottom floor's `.agent-office/` names, else the bottom floor. Like the dog he's sent a leg at a time (the route, its speed, what he does at the end), on a grid of his own: the dog's with the doorways and the floor in front of them taken out, so he stays out of doorways, off the stairs and out of the meeting room. He looks where the dog is headed before he sets off, waits for it to pass and steps aside when it comes at him; the dog doesn't know he's there. A pat is checked for reach by the office and has him follow whoever gave it for about a minute. When that person takes the elevator, he rides after them only if they're an admin, since which floor has the goat is the building's for everyone, and `goat.json` is rewritten with the floor he got out on. A floor removed with him on it sends him back to the bottom one.
- **The arcade.** The four games (`src/client/features/arcade/`) are the same instances on the lounge cabinet and on the boss's monitor, and each has one high-score table for the building, kept as one list in the office's `arcade.json` (a row with no `title` is Blockfall's, so scores from before the other games carry over). A score isn't taken on a browser's word: the game sends a frame of its screen as it goes, the office checks each against what that game allows (Blockfall frame by frame as before; 2048's score against what its tiles are worth and its tiles against its moves; a snake no longer than its steps could feed it; Minesweeper timed by the office's own clock, with a 3 second floor) and puts the score up itself. Names and colors come from the session. The same frames are what everyone else on the floor sees on the cabinet, relayed by the office; Minesweeper's never say where the mines are until the game is lost. A game on the boss's monitor is followed for its score the same way, but doesn't take the cabinet and isn't relayed. The checks are for plausibility, not a replay, so a scripted browser could still post the best score possible at the allowed pace.
- **Long shots and heaves.** Up to 16 m from the hoop (`RANGE` in `src/shared/hoop-range.ts`) a shot is worked out as it always was (`shared/hoop.ts`): the speed through the middle of the ring at the angle you throw, and the meter's green is how far off that you can let go. Further out the green is `greenWidth(dist)`: 16/dist of its old width, never under 0.04 of the meter. From 22 m (`HEAVE_FROM`) it's a heave: the meter runs up in 0.7 s instead of 1.05, and the throw goes no steeper than 0.6 rad, as steep as it can and still clear the ceiling, up to 28 m/s. Only the middle of the green is sure to go in out there: `makeWidth` of the meter, 15.5% of the green (a little less than goes in from anywhere just inside 16 m, where it's down to physics: 13 to 25 ms of the meter), never under 0.01 of it. So just past 16 m it's about 13 ms of the meter, shrinking with the green to 10.5 ms, and a heave's 7 ms on its faster meter: as hard as it gets and still there to hit (`tests/hoop-range.test.ts` scans release times to hold it to that). The ball comes in too flat to drop through the middle of the ring clean, so the page works out what does go in while you wind up (`farShotSteps`, a few trial throws a frame and no more than 2 ms of it, in `features/basketball/long-shot.ts`; letting go finishes it if you've moved since): it flies the throw at speeds round the ideal one, with the same steps every page and the office fly it, against the backboard and its arms, the ring, the floor, the wall and the ceiling, out from the ideal either way to where they stop dropping in, and maps the middle of the green onto the stretch of speeds the ideal throw itself drops in with (so the middle of the green goes in the way the ideal does, not off the glass every time), or the widest stretch where the ideal rattles out at every angle it tries (a little flatter, up to 0.12 rad). Between two speeds that drop in there can be one that rattles out, so a release in the middle goes at the nearest speed that was tried and dropped in, thrown from exactly where it was worked out (a hundredth of a millimeter from your hands at most): it goes in for sure. Either side of the middle the speed goes off as it does either side of the sweet spot inside 16 m, squeezed into the smaller green, so from some places a little late still banks in. Outside the green nothing goes in, anywhere on the meter. A throw faster than anyone throws two-handed (`BALL.maxSpeed`), which only a heave is, is dead once it has touched the ceiling: it drops through the ring without counting (`step` in `shared/hoop.ts`, which the office flies too). Any other throw let go of outside the green that would still find a way in (a little long off the glass and the back of the ring, short and up off the floor, or along the hoop's wall up off the ceiling and back off the far wall) goes a little further off, a thousandth of the ideal speed at a time, or once it's as hard (or as soft) as it goes, a hundredth of a radian steeper or flatter, until it misses past the room as the page has it (`farRelease`). `tests/hoop-range.test.ts` sweeps the whole meter from spots across the floor to hold it to all that. A long shot is only on where the ball has a clear way to the ring (`clearWay`): from inside the room, never from over or under the corner loft's deck, and with nothing of the room as the page has it (the loft's glass and floor, the glass room, the elevator, the fire pole, tall furniture) anywhere a throw of the green's might go, until it's nearly at the hoop; elsewhere it's a toss. Nothing about a heave is sent: everyone's page tells one from the throw itself (from 22 m out, straight at the ring: `heaveThrow`) and shows its thrower's arm come over the top.
- **The hoop's scoreboard.** The office keeps who has the ball and how it was last thrown (`src/server/court.ts`), and now flies every throw it passes on itself, the same way every page does (`flyShot` in `src/server/shot-judge.ts`, stepping `shared/hoop.ts`): past the backboard, its arms and the ring, the floor, the outside walls and the ceiling, the floor's furniture as its layout has it, the big mezzanine and the Steps. A page never says it scored, or from how far. A make counts as the ball drops through the net, measured along the floor from where it left the hand to the middle of the ring, to a tenth of a meter, and only if it left their hands where the office last saw them standing (within 1.2 m of their last `move`, and between 0.8 and 2.9 m above their feet); it's credited no further out than where they stood and half a step (`creditedDistance`), and no further than the floor's farthest corner from the hoop. The table (`src/server/longshots.ts`) is the building's, in `hoop.json` beside `arcade.json`: one row a person (their account, or their name on the shared password, from the session), their longest, the top ten. A throw is flown at most every 400 ms per person. A better make goes on the table at once, and the building hears about one person's makes at most every 3 s (a better one sooner than that is told about when the time's up). What the office only has on a page (the kitchen, the corner loft and the glass room, the elevator, the desks) it doesn't fly past, so a ball that only goes in off one of those counts the office's way; a page only offers a long shot where none of those is anywhere a throw of the green's goes (`clearWay`, above). A page flies a throw past each thing in its way once (`ballSolids` in `features/basketball/world.ts`): the hoop's fixture puts its backboard and arms on the floor's list once, and what's on it twice (some of the office's own furniture is) is flown past once, so a heave that goes through the thin board into its arms comes out of them the same way on a page and in the office (`tests/hoop-colliders.test.ts`). What a determined cheater can still do: the office trusts the positions a browser sends (it doesn't check walking speed or walls) and the throw's numbers, so a scripted browser can say it's standing anywhere on the floor and send the throw that drops in from there (`idealSpeed`, or `farShot` from way out), and every make it posts is one the ball really could make from where it says it stood, no faster than anyone throws (28 m/s, a heave's top speed) and under the ceiling. It can't post a distance the physics doesn't allow, put up someone else's name (an account's is its own), or have it announced faster than the limits. A game of PIG (`src/server/pig.ts`, with the rules pure in `src/shared/pig.ts`) is the office's too: invites (both at the court, 10 m of the hoop, and two people: not the same account, or name on the shared password, in two tabs), whose turn it is, the spot to match (worked out from the leader's throw: where they stood is 0.3 m back along its way), each shot's result from the same flight, the letters and the winner. A throw out of turn, mid-shot or from outside the ring (half a meter, and a tenth for slack) is refused before the court takes it, and the ball stays in the thrower's hands. The ball is handed to whoever's turn it is (`Court.hand`) and is theirs alone to pick up (`Court.reserve`, which pages see as `BallState.for`). A player who's away (up off the floor's own level, like the loft, off the floor or out of the office; anywhere else on the floor is still the court, as there's a long shot from nearly all of it) for 20 s forfeits; someone back on a new connection as the same account or name takes their place. A win goes on the tally when the loser spells PIG, or forfeits once each player has had a shot (giving up straight away is no win). The office looks at each game every second, and a floor whose hoop has come down (a layout saved without it) has its game called off, no contest: the ball is anyone's again and both players are told. A scripted browser can make every shot in PIG the same way.
- **The gong.** Each time the office fetches the PR list, a PR that was open last time and is merged now rings the gong. A merge from the PR window rings as soon as `gh pr merge` returns, and isn't rung again when the list catches up. Anything else shows up at the next fetch: about every 90 seconds while someone is on the floor, and right after a queue task finishes. The gong is synthesized like the other sounds, so the volume and mute under **⚙️** apply to it.
- **Golf.** A shot is three numbers, its heading, loft and power, sent to everyone on the floor, along with which tee it came off on a floor with two (the office adds that from the bay it has the golfer on: `PeerInfo.golfBay`, set by the `act` message's `golf` and `bay`). The bays' positions are in `src/shared/tees.ts`; a floor's tee count is `RoomOptions.tees`, saved with its layout. Each browser works out the flight from those the same way, a fixed 240 steps a second: gravity and a little drag, the balcony's railing and wall, the neighbours' walls and roofs, the balconies further down, then bounces and a roll that depend on what it lands on (green, fringe, fairway, rough, sand or road), and the cup. So everyone sees the same ball land in the same place without it being streamed. The hitter's browser adds a little mishit to the numbers before sending them, so no two swings are exactly alike.
- **Main Street, Putt Street and Friday One.** The street out front is one street for the whole building, in a frame of its own (`shared/mainstreet.ts`): every floor draws it as far below as that floor is up, and the roof bar draws it too. What stands on the plots is the office's `street.json`, and everyone is sent each business's public card only. The office checks every claim, change and release itself: from a street admin (an admin, asked fresh each time), and never with anyone, on any floor's street, or Friday One where walls would go up. On Putt Street the office is the referee. A putt is a heading, a power and when the putter meets the ball, which the office holds to 20–150 ms after it hears it, so nobody picks when the windmill's sails are open; it rolls the putt with the shared physics (`shared/minigolf/physics.ts`, 240 steps a second) and sends everyone the path, 30 samples a second, which every page plays back on the office's clock. No page decides where a ball stops or what anyone scored. Friday One is flown by its pilot's page (`fly` in `shared/heli.ts`, a fixed 1/60 s step), which sends its pose about fifteen times a second; the office checks each one against the same solids and ground (`shared/heli-world.ts`), how fast it could have got there and, for a landing, who's under it on every floor and every floor's cars, and snaps the pilot back to the last good pose when it won't do. Everyone else's page smooths it between poses. With nobody at the controls mid-flight it flies itself home on a timer of the office's own, out from under anything over it first; a trip home that gets nowhere for 20 s ends with it set down where it is, if it may land there, or put back on its pad. Each of the three keeps one file in the office's `.agent-office/`, written whole and renamed into place with mode 600; one that won't read is logged, treated as empty (Friday One starts on its pad), and moved aside as `<name>.corrupt-<ms>` before the next write, so nothing in it is lost.
- **Jukebox.** Each floor's `jukebox.json` says only what's on and when it started, so it keeps playing through a restart. Every browser plays it for itself: a tune is decided note by note by its bar and step, so starting from the same moment is enough for everyone to hear the same thing. To agree on that moment, each page pings the office a few times on arriving and keeps the quickest answer to line its clock up with the office's. A tune is drums, bass, an FM electric piano and a melody picked from the chord tones, with record crackle and tape wobble, in 32-bar rounds. It's scheduled a second ahead on a timer rather than each frame, which lets it carry on in a background tab. It goes through a panner at the jukebox and a filter that muffles it with distance. Most streams can't be routed through Web Audio without CORS, so a stream plays in a plain `<audio>` element, turned down by hand on the same distance curve. An audio file seeks to where everyone else is. A YouTube track is `track: 'youtube'` with `video: { id, title, by }` (and `name`, the label someone typed, which a pasted stream can have too). When the link is pasted the office asks YouTube's oEmbed endpoint once for the title and the channel (`src/server/jukebox-video.ts`), which is also how it learns a video can't be embedded; that is the only request the office makes to YouTube for it. Each browser plays the video itself (`features/jukebox/video.ts`) on the lounge TV through `world/webscreen.ts`, starting at (office clock − `startedAt`) modulo the video's length and seeking again when it's more than 2 s out (`features/jukebox/sync.ts`, tested in `tests/jukebox.test.ts`). Its volume is `OfficeSound.musicHeard()`: your music volume with the same fall-off by distance from the jukebox as a stream. `features/tv` decides what the TV shows: a shared screen first, then the jukebox's video, then the idle card. While a screen is shared the video plays in `features/jukebox/dock.ts`, a docked player in the HUD.
- **Floors.** `floors.json` in the office's `.agent-office/` lists the floors: each one's checkout and colors. Adding one runs `gh repo view` (does this login see it, and what's its exact name), then `gh repo clone` into the projects folder; a checkout that's already there from the same repository is used as it is (one whose clone was cut off, with nothing checked out, isn't). The clone runs in a session of its own with no terminal, so nothing can stop to ask a question nobody sees, and git's progress goes to a log in `.agent-office/clones/`, which the office reads every second for the elevator panel. A log that stops growing for 3 minutes means the clone is stuck, and it's stopped. The clones under way are kept in `cloning.json`: an office restarted mid-clone (tsx watch, systemd) picks them up and carries on, while Ctrl+C stops them. Each floor runs its own workers, GitHub boards, queue and changes watcher in its checkout. A floor nobody is on, with nothing running, asks GitHub about its boards every 10 minutes instead of every 90 seconds. People get only the moves, worker updates and terminal frames of the floor they're on; the chat, voice connections and the budget are the building's.
- **The building's outside.** Each browser draws it for itself from the floors list; none of it is saved. `src/client/world/facade.ts` holds its colors (`FACADE`), the tower's shape (`TOWER`: 15 storeys, the three glass bars by storey and length, the glass, spandrel and mullion sizes, the seams) and its name and lockup (`BUILDING`), with no three.js in it. The tower is `Math.max(floors, TOWER.storeys)` storeys tall, and the roof stands on as many (`roofFloors()` in `features/rooftop/index.ts`). Fifteen, because from the roof of a taller one the street would be further down than the office lets anyone arrive (`arrivalSpot` in `src/server/office/input.ts` stops at `streetBelow(MAX_FLOORS - 1)`). The real floors are the bottom storeys and keep their heights, so the exit stair, the balconies, golf and the parachute are where they were. The storey you're on is the office itself (`world/office/`); the other real storeys, and the drawn ones over them up to the crown, are `world/tower.ts` and `world/tower-bars.ts` (above you, planes with nothing to bump into; below you, the storeys' walls and the garage's ceiling are solid), with the storeys' names and the lockup from `world/tower-signs.ts`, the mast to stand under up on the roof from `features/rooftop/mast.ts` (`tower.ts` draws a plainer one to see from below) and the garage's marquee, lane and directory from `world/forecourt.ts`. A storey's name and color come with the floors: `FloorInfo.look` is the paint the office builder gave the floor (its `FloorPlan.look`), and the office sends the list again when a layout is saved; `floorStoreys()` (`core/floors.ts`) takes the trim of that paint, or of the floor's own, and `syncStack()` (`core/travel.ts`) hands them to `setStoreys()` before the building is drawn again, which it is whenever they change (`storeysKey()`). The upper windows are twelve entries in `WINDOWS` from `shared/clerestory.ts`, where `columnsOf()` says which windows stand one over another, so the office's walls and the tower's planes leave both open.
- **The rooftop.** Nobody works up there, so the roof isn't a floor: it's a place (`@roof`, which no floor id can be) that people are on, with none of a floor's workers, boards or queue. The DJ's set is endless and needs no state: its tracks, their keys, grooves and basslines, and where each one is follow from the office's clock, like the jukebox's tunes, so everyone up there hears the same bar, and the lights flash on the same kicks and snares even for someone with the music off. Drum and bass at 172 BPM, synthesized in the browser: a two-step break, a reese bass through a filter that opens and closes on the eighths, a sub, pads, an arpeggio, risers into each drop and an air horn when one lands. Being drunk is just your own browser's: while you are, the frame is drawn into a texture and onto the screen through a shader that doubles, smears and ripples it. With reduced motion on, nothing sways or strobes.
- **State.** The office's `.agent-office/` (in `~/agent-office`, or in the project you started it in) holds the password, the signing secret, the accounts and open invites (`accounts.json`), each account's own Claude, GitHub and git sign-ins (`homes/<account>/`), the floors (`floors.json`) and the clones on their way (`cloning.json`), the chat, the spend, the arcade's high scores (`arcade.json`), the hoop's longest shots and PIG winners (`hoop.json`), the businesses on Main Street (`street.json`), Putt Street's records (`minigolf.json`), where Friday One is parked (`heli.json`) and whether workers go home once their PR merges (`leave-on-merge.json`). Each floor's checkout has its own `.agent-office/` with the hook settings, the saved workers and their scrollback, the task queue, the pictures on the walls (`decor.json`), the dog's name (`dog.json`), which floor the goat lives on (`goat.json`, in the bottom floor's only), the jukebox (`jukebox.json`), the whiteboard (`whiteboard/`) and the meetings (`meetings.json`, and each meeting's notes in `meetings/`) and, for DeepSeek Harness workers, the profile patch (`dsh-patch.yml`) with their session logs under `dsh-sessions/`. It is added to `.git/info/exclude` automatically, so it never shows up in `git status`. The one thing the office writes outside it is a Cursor worker's hooks, which the Cursor CLI only reads from `.cursor/hooks.json` in the folder it runs in: they're there while the worker runs, and excluded from git the same way (see [Choosing an agent](agents.md)).

## Security notes

Anyone who can sign in can drive Claude Code, OpenCode, Codex, Grok, Muse, DeepSeek Harness, Pi or Cursor in that directory, and through it run commands as the user that runs the office. Treat the password, the accounts and the invite links like SSH access:

- The office listens on `127.0.0.1` unless you pass `--host`, and `deploy/provision.sh` keeps it there, behind SSH, Caddy or Tailscale Serve. The sign-in link the terminal prints works once, and the office keeps only a hash of it, in memory.
- Roles decide what the office's own windows and messages allow: managing floors, the office builder, a floor's boards and agents, accounts, prompts and the worker limit are the admins'. They are not a sandbox: a member's workers and shells run as the same user as the office, on the same machine. And the shared office password is an admin, so roles only mean something once it's switched off.
- Use a strong password and HTTPS. With `--trust-proxy`, cookies are `Secure` once the proxy says the request came over https.
- Changing the shared password signs out everyone who came in with it, because those sessions are signed with a key derived from it. Account sessions carry the account's id and are checked on every request, so revoking an account, or switching the shared password off, signs those people out at once, open connections included. Account passwords are stored as scrypt hashes, and invite links carry their token after the `#`, so it never reaches a server log. Login and invite attempts are limited to 10 per 5 minutes per client.
- Only enable `--trust-proxy` behind a proxy that appends `X-Forwarded-For` (Caddy and nginx both do). The office uses the rightmost hop.
- Run the office as a dedicated, unprivileged user, in the project you mean to share.
- The WebSocket checks the session cookie and the `Origin` header. The hook endpoint only listens on loopback and needs a random per-worker token.
- On a Tailscale office, Tailscale's access controls decide who reaches the machine, and they reach every port that listens on all interfaces, not just the office. The security group doesn't apply to tailnet traffic. The `agent-office-serve` helper the office runs as root only ever points a port above 1023 at the office's own port.
- `agent-office tunnel` signs in with the office password or an account, like a browser, and keeps the session (not the password) in `~/.config/agent-office/tunnel.json`, readable only by its user. The ports it opens listen on `127.0.0.1` and `::1` only and take requests for `localhost` names only, so another site can't reach them by pointing a name of its own at them. Anything on that computer can use them without the office's sign-in, the way it could use a dev server running there. A request the tunnel sends is only ever relayed to a worker's server: when nothing serves the port it names, it gets the *Not running* page, never the office's own pages.
- Service tunnels are relayed only to web servers a worker started, and only with an office session. The office's own cookies are stripped before a request reaches that server. A server you started yourself outside the office is never listed or relayed.
- Workers don't inherit the office password or any parent agent-session variables.
- Workers hired by an account run on that account's own sign-ins (`CLAUDE_CONFIG_DIR`, `GH_CONFIG_DIR` and `GIT_CONFIG_GLOBAL` under `.agent-office/homes/<account>/`), and never see the machine's own Claude or GitHub credentials (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `GH_TOKEN` and the like are taken out of their environment). But every worker runs as the same OS user, so one person's worker *can* read another person's folder. Per-person sign-ins keep work attributed and plans separate. They don't keep teammates' secrets from each other.
- The picture fetcher (`/api/image`) needs an office session. It fetches any http(s) link it's given, from the office's machine. That gives nobody new reach: anyone signed in can already run `curl` from a shell worker. Pictures are served with a sandboxing `Content-Security-Policy`, so an SVG can't run script on the office's origin.
